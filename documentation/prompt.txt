# FastNote — High-Performance Minimal Linux Text Editor

## Role

You are an expert systems programmer specializing in C, Linux desktop applications, SDL3, text rendering, and performance-oriented software architecture.

Your task is to implement **FastNote**, an extremely lightweight and fast graphical text editor for Linux.

The primary goals are:

1. Extremely fast startup.
2. Very low memory usage.
3. Minimal CPU usage while idle.
4. Responsive keyboard and mouse input.
5. Simple and maintainable C code.
6. Minimal external dependencies.
7. A small and clean user interface.
8. No unnecessary features or abstractions.

Do not over-engineer the application.

---

# 1. Technology Requirements

Use:

* **C17**
* **SDL3**
* **FreeType**
* Standard C library
* POSIX APIs where appropriate
* CMake

Do NOT use:

* GTK
* Qt
* wxWidgets
* Electron
* Tauri
* Scintilla
* GtkSourceView
* ImGui
* OpenGL
* Vulkan
* Rust
* C++
* JavaScript
* Python

SDL3 should be responsible for:

* Window creation
* Window resizing
* Keyboard input
* Mouse input
* Clipboard integration
* Event processing
* Basic rendering

FreeType should be responsible for font loading and glyph rasterization.

Avoid introducing additional dependencies unless there is a strong technical reason.

---

# 2. Target Platform

The initial target is:

* Linux
* X11 and/or Wayland through SDL3
* x86_64
* Desktop environment

The application must work correctly when the user resizes the window.

The UI should adapt dynamically to the available window dimensions.

---

# 3. Application Philosophy

FastNote is intentionally NOT a full-featured IDE or Notepad++ replacement.

It is a minimal text editor.

The first version should focus on:

* Opening files
* Editing text
* Creating documents
* Saving files
* Saving files under a new name
* Basic clipboard operations
* Basic navigation
* Adjustable font size

Do not implement syntax highlighting.

Do not implement plugins.

Do not implement tabs.

Do not implement autocomplete.

Do not implement code intelligence.

Do not implement a project system.

Do not implement a complex settings system.

Do not add functionality simply because other text editors have it.

# 7. Font

Use FreeType.

Default font size:

```text
14 px
```

Allow the user to change the font size.

Suggested range:

```text
8 px → 48 px
```

Keyboard shortcuts:

```text
Ctrl + Plus     Increase font size
Ctrl + Minus    Decrease font size
Ctrl + 0        Reset font size to 14 px
```

The font size must be configurable at runtime.

Do not reload the font for every glyph.

Load the font once and maintain an efficient glyph cache.

---

# 8. Glyph Rendering

Implement a glyph cache.

Do NOT rasterize the same glyph repeatedly.

Conceptually:

```c
typedef struct {
    uint32_t codepoint;
    SDL_Texture *texture;
    int width;
    int height;
    int bearing_x;
    int bearing_y;
    int advance_x;
} Glyph;
```

The cache should contain glyphs that have already been rasterized.

When a glyph is needed:

```text
Glyph requested
      │
      ├── cached → use existing texture
      │
      └── missing → FreeType rasterization → cache
```

Only render visible text.

Do not render lines outside the visible viewport.

---

# 9. Text Buffer

Create a dedicated text buffer abstraction.

Initial implementation can use a contiguous dynamically allocated buffer:

```c
typedef struct {
    char *data;
    size_t length;
    size_t capacity;
} TextBuffer;
```

Required operations:

```text
insert
delete
append
clear
load
save
```

Use efficient capacity growth.

Do not realloc the buffer for every typed character.

Use exponential growth such as:

```text
new_capacity = old_capacity * 2
```

or another reasonable strategy.

---

# 10. Text Encoding

The initial implementation should use UTF-8.

Files should be treated as UTF-8 text.

Do not implement automatic encoding detection in V1.

If a file contains invalid UTF-8, handle it gracefully instead of crashing.

The editor should never crash because of malformed input.

typedef struct {

# 12. Keyboard Input

The editor must support normal Linux keyboard layouts.

# 15. Scrolling

The editor must support vertical scrolling.

Horizontal scrolling is optional for V1 but the architecture should not prevent adding it later.

Only visible lines should be rendered.

For example, if the document contains:

```text
100,000 lines
```

and the window displays:

```text
40 lines
```

the renderer should primarily process those approximately 40 visible lines.

Do not render the entire document every frame.

# 17. Main Loop

The main loop must be event-driven.

Do not run the application at an unnecessarily high fixed FPS while idle.

Conceptually:

```text
while application_running:

    process_events()

    if state_changed:
        render()

    wait_for_events_or_frame()
```

The application should consume very little CPU while the user is not interacting with it.

However, cursor blinking should continue normally.

A reasonable cursor blink interval is approximately:

```text
500 ms
```

Do not busy-wait.

Do not use:

```c
while (true) {
    render();
}
```

with no throttling.

Use SDL's event/wait functionality appropriately.

# 23. Performance Requirements

Performance is a primary feature.

Follow these rules:

### Startup

Avoid expensive initialization.

Do not:

* scan the filesystem
* load unnecessary resources
* initialize unused subsystems
* preload thousands of glyphs

Only initialize what is required.

### Rendering

Only render visible text.

### Memory

Avoid unnecessary copies of the document.

Avoid temporary allocations inside the rendering loop.

Avoid allocating memory for every character.

### Input

Keyboard input must feel immediate.

### Idle CPU

CPU consumption should be close to zero when the application is idle, except during cursor blinking or necessary OS/UI events.

### File loading

Use efficient buffered file I/O.

For large files, avoid repeatedly reallocating memory.

# 24. Error Handling

Never crash on normal user errors.

Examples:

* File does not exist
* Permission denied
* File cannot be saved
* Invalid UTF-8
* Out-of-memory condition
* Font cannot be loaded
* SDL initialization failure

Errors should be reported cleanly.

Use stderr/logging for developer diagnostics.

Do not spam stdout/stderr during normal operation.

# 26. Code Quality

Use modern C17 practices while keeping the implementation simple.

Requirements:

* No global mutable state unless genuinely necessary.
* Clear ownership of allocated memory.
* Every allocation must have a clear owner.
* Every resource must have a cleanup path.
* Avoid hidden side effects.
* Avoid unnecessary abstractions.
* Prefer simple structs and functions.
* Keep functions reasonably small.
* Document non-obvious performance decisions.

The code should be easy for another C developer to understand.

---

# 27. Memory Safety

Pay particular attention to:

* buffer boundaries
* UTF-8 boundaries
* cursor offsets
* selection offsets
* realloc failures
* SDL resource destruction
* FreeType resource destruction
* file handles
* clipboard data

The application must not have obvious memory leaks.

Test using tools such as:

```bash
valgrind
```

when available.

Also use sanitizers during development:

```text
-fsanitize=address
-fsanitize=undefined
```

FastNote V1 is complete when the user can:

1. Launch FastNote.
2. See the editor window immediately.
3. Type UTF-8 text.
4. Navigate using the keyboard.
5. Select text.
6. Copy/cut/paste text.
7. Create a new document.
8. Open a file.
9. Edit the file.
10. Save the file.
11. Save the file under a different name.
12. Resize the window.
13. Scroll through the document.
14. Change the font size.
15. Close the application.

The application must:

* remain responsive,
* not crash during normal operation,
* use very little CPU while idle,
* avoid unnecessary memory allocations,
* render only visible text,
* clean up all resources correctly.

# 32. Final Engineering Principle

When choosing between two valid implementations, prefer:

```text
simpler
      +
fewer dependencies
      +
less memory
      +
less CPU
      +
lower latency
```

over:

```text
more features
      +
more abstractions
      +
more dependencies
```

FastNote should feel like a small native Linux utility rather than a web application or a heavyweight desktop application.

Before implementing a feature, ask:

> "Does this directly contribute to the minimal text-editor experience or its performance?"

If the answer is no, do not implement it.

Start with Milestone 1 and proceed incrementally. After each milestone, build the application, verify that it works, and only then proceed to the next milestone.
